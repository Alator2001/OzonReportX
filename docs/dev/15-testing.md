# 15. Тесты

```bash
.venv/Scripts/python.exe -m unittest discover -s tests   # Windows
.venv/bin/python -m unittest discover -s tests           # macOS
```

Только так: тесты импортируют друг друга как модули верхнего уровня (`import test_technical_fixes`),
поэтому `python -m unittest tests.test_x` падает на импорте. Один файл:

```bash
.venv/Scripts/python.exe -m unittest discover -s tests -p "test_promos_v2.py"
```

`pytest` в зависимостях нет. Полный прогон — около 220 тестов за ~10 секунд.

## Правила

- **Без сети.** Все ответы Ozon и WB подменяются через `unittest.mock`. `test_technical_fixes.OfflineTests.setUp`
  дополнительно отключает сетевые вызовы и перенаправляет вывод; многие тесты переиспользуют этот `setUp`.
- **Без пользовательских файлов.** Временные файлы — в `.cache/technical-fix-tests/` (через `tempfile`),
  `costs.xlsx` и отчёты пользователя не трогаются.
- Чистую логику (расчёты, планы) выносите в функции без сети — их легко проверить на подставных данных
  (`build_plan`, `analyze_product`, `analyze_item`, `plan_upcoming_action_items`, `action_exit_price`).
- Для изменений, которые отправляют что-то во внешний API, проверяйте **точный payload** (адрес, тело, единицы
  денег) — именно здесь ломается при переходах Ozon на новые версии методов.

## Чего тестами не проверить

- **Реальное поведение Ozon.** Тесты фиксируют наше понимание API. После изменений у Ozon (новые версии, «единая цена»)
  проверяйте на живом магазине запросами на чтение и безопасными запросами записи (см. [03](03-ozon-api.md#переходы-на-новые-версии-октябрь-2026)).
- **Интерфейс Flet.** Отрисовка не тестируется; после правок `app_flet.py` откройте затронутые экраны вручную.
