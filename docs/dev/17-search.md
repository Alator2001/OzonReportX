# 17. Поиск и ключевые слова

Раздел собирает собственную историю поисковой аналитики Ozon: по каким запросам находят товары
магазина и сколько покупателей искали каждый запрос, а также продажи по дням. На этих данных строятся
семантика, позиции в выдаче по регионам и A/B-тесты карточек (следующие этапы).

Статус: **этапы 1–3 и экран «Поиск»** — сбор официальных данных Seller API, семантика, парсер выдачи по регионам,
раздел приложения. Эксперименты (A/B) — следующий этап; профили регионов и импорт CSV — из командной строки.

## Что отдаёт Ozon без подписки

Проверено запросами 23 октября 2026 на магазине без Premium.

| Метод | Что приходит | Что пусто |
|---|---|---|
| `/v1/analytics/product-queries` | по SKU: `unique_search_users` | `position`, `unique_view_users`, `view_conversion` — `null`; `gmv` — 0 |
| `/v1/analytics/product-queries/details` | по SKU и запросу (до 15 запросов на SKU): текст, `query_index`, `unique_search_users` | позиция и просмотры — `null`; `order_count`, `gmv` — 0 |
| `/v1/analytics/data` | `ordered_units`, `revenue` по SKU и дню | метрики поиска молча выбрасываются из ответа |
| `/v1/search-queries/text`, `/top` | — | 403: только Premium Pro |

Следствия:
- **Позиций в API без подписки нет.** Позиции будут только из парсера выдачи (этап 3).
- `unique_search_users` по запросу — единственная частотность. Это покупатели, которые искали этот запрос
  и могли увидеть товар, а не частотность запроса по всему Ozon.
- Поля, доступные только с подпиской, сохраняются как пришли (`NULL`). Если подписка появится, они начнут
  заполняться без изменений кода.
- Данные за последний месяц доступны за любой день; старше — только с подпиской. Поэтому историю нужно копить
  с первого дня: пропущенный месяц потом не восстановить.

## Границы дня

Ozon трактует период как полуинтервал `[date_from, date_to)` в UTC: `date_from = date_to` даёт пустой ответ,
день D — это `D 00:00Z … D+1 00:00Z` (`search_api.day_bounds`).

**Без подписки день D доступен в product-queries только с полуночи D+2 (UTC)**: запрос за вчера возвращает
403 «Analytics for the specified period is available starting from the premium subscription». Поэтому запросы
собираются по позавчерашний день (`QUERIES_LAG_DAYS = 2`), продажи из `/v1/analytics/data` — по вчерашний
(`SALES_LAG_DAYS = 1`). Ozon досчитывает данные 1–2 дня, поэтому последние 3 дня окна перезагружаются при каждом запуске.

`/v1/analytics/data` принимает даты без времени; дни в его ответе — дни Ozon (вероятно, московские).
Для сравнения «до/после» в экспериментах это не важно: окна сдвигаются одинаково.

## Модули

| Модуль | Что делает |
|---|---|
| `scripts/search_db.py` | Подключение к `search data/search.db`, миграции (`MIGRATIONS`: up и down), upsert-функции, журнал сбора |
| `scripts/search_api.py` | Запросы к Seller API через `report_http.create_session()` (темп, повторы при 429 и 5xx, таймаут 60 с), разбор ответов |
| `scripts/search_collect.py` | CLI ежедневного сбора: товары → запросы по дням → карточки → продажи по дням → пересчёт семантики |
| `scripts/search_semantics.py` | Леммы, частотность, кластеры, матрица покрытия карточки, приоритет и зона роста, ручной ввод и импорт CSV |

`search_api` читает ключи при каждом запросе (`_headers()`), а не при импорте — приложение импортирует `search_db`
и не должно падать без ключей Ozon.

## База

SQLite, файл `search data/search.db` (исключён из Git, переносится `transfer_data.py`, не трогается автообновлением).

| Таблица | Ключ | Что внутри |
|---|---|---|
| `products` | `sku` | `product_id`, артикул, название |
| `keywords` | `id`, уникален `query` | текст запроса как его отдал Ozon или ввёл пользователь; `normalized` (нижний регистр, ё → е, пробелы); `lemma_key`; `cluster_id` и `cluster_locked` (кластер выбран вручную); `frequency` и `frequency_source` (`api`, `manual`, `csv`); `priority` |
| `sku_keywords` | `(sku, keyword_id)` | связь товар — запрос: источник, `is_target` (целевой запрос), `manual_priority`, `score` и `score_details` (JSON с составляющими) |
| `query_stats` | `(date, sku, keyword_id)` | статистика запроса за день: `searched_users`, `viewed_users`, `view_conversion`, `position`, `orders`, `gmv`, `query_index` |
| `sku_daily` | `(date, sku)` | по товару за день: поисковые поля из product-queries и `ordered_units`, `revenue` из analytics/data |
| `clusters` | `id`, уникален `lemma_key` | кластер запросов: ключ лемм главного запроса и его текст как название |
| `card_snapshots` | `(date, sku)` | снимок карточки на день: название, описание, характеристики (JSON), фото, хеши каждой части |
| `collect_runs` | `id` | журнал: источник, день, время, статус `running/ok/denied/error`, сообщение |
| `schema_version` | — | номер применённой миграции |

Отличие от исходного ТЗ: вместо `search_funnel` с кликами и корзинами — `query_stats`, потому что кликов и корзин
по запросу в API нет (даже с подпиской).

### Миграции

```bash
.venv/bin/python scripts/search_db.py version
.venv/bin/python scripts/search_db.py migrate          # до последней
.venv/bin/python scripts/search_db.py migrate --to 0   # откатить всё
```

`connect()` сам применяет недостающие миграции. Каждый шаг — отдельная транзакция: упавшая миграция откатывается
целиком, номер версии не меняется. Новую миграцию добавляйте в конец `MIGRATIONS` с парой up/down; старые не правьте.

### Идемпотентность

- Все записи — `INSERT … ON CONFLICT DO UPDATE` по ключу таблицы.
- `upsert_sku_daily` обновляет только переданные поля: product-queries и analytics/data пишут в одну строку
  разные столбцы и не затирают друг друга.
- День запросов пишется одной транзакцией; если любая страница не загрузилась, день не сохраняется и не помечается собранным.

## Сбор

```bash
.venv/bin/python scripts/search_collect.py                       # пропущенные дни за 28 дней + 3 последних заново
.venv/bin/python scripts/search_collect.py --days 7 --refresh 1 --skip-sales
```

1. Список товаров: `/v3/product/list` (все, с защитой от повторного `last_id`) → `/v3/product/info/list` → `products`.
2. Для каждого дня, которого нет в журнале со статусом `ok` (и для последних `--refresh` дней):
   product-queries по всем SKU → details только для SKU, которых кто-то искал → `sku_daily`, `query_stats`, `keywords`.
3. Продажи: один диапазон от первого до последнего нужного дня в `/v1/analytics/data` (`dimension: [sku, day]`).
   Перед каждым вызовом проверяются квота (45 из 50 в сутки, по журналу `analytics_data_request` с полуночи UTC)
   и пауза 61 с после прошлого вызова — в том числе сделанного прошлым запуском.

Ошибки:
- **403** — источник помечается `denied`, в лог пишется понятное сообщение, сбор продолжается без него. Код выхода 0.
- Любая другая ошибка — источник останавливается на этом дне (`error`), следующий запуск догрузит. Код выхода 1.
- Второй одновременный запуск сразу выходит с кодом 2 (блокировка `file_lock.exclusive_file` на файл базы).

### Ежедневный запуск

Своего планировщика у приложения нет. `auto_collect_search` (`app_flet.py`, вызывается в конце `initialize_app`)
при каждом запуске приложения проверяет `search_db.collected_today()` и, если сегодня (UTC) сбор ещё не завершился
успешно, запускает `search_collect.py` отдельным процессом в фоне. Без `job_lock`: сборщик только читает Ozon.
Вывод пишется в журнал сессии; при частичной ошибке показывается уведомление, если в этот момент нет задачи пользователя.

Если приложение открывают не каждый день, пропущенные дни догрузятся при следующем запуске (в пределах месяца,
который хранит Ozon). Для сбора без приложения можно поставить `search_collect.py` в launchd (macOS)
или Планировщик заданий (Windows).

## Карточки

`/v4/product/info/attributes` по списку SKU (до 1000 за запрос, курсор `last_id`) отдаёт всё сразу, отдельный
`/v1/product/info/description` не нужен. Атрибуты с особым смыслом (`search_api.parse_card`):

| Атрибут | Что это | Куда идёт |
|---|---|---|
| 4180 | «Название» | не дублируем — берём `name` |
| 4191 | «Аннотация» | описание |
| 11254 | Rich-контент (JSON) | только хеш — для поиска изменений; в покрытии не участвует |
| 9024 | «Артикул» | пропускаем |
| остальные | характеристики, включая хештеги (23171) | `attributes` |

Снимок пишется раз в день (повторный запуск в тот же день перезаписывает его). Хеши частей (`name_hash`,
`description_hash`, `attributes_hash`, `images_hash`, `rich_content_hash`) нужны этапу экспериментов
для автоматического поиска изменений карточки.

## Семантика

Пересчитывается в конце каждого сбора (`search_collect.update_semantics`) и командой
`python scripts/search_semantics.py rebuild` — одной транзакцией, ~0,2 с на 2 тыс. запросов. Без `pymorphy3`
сбор данных работает, а шаг семантики пишет ошибку в журнал.

### Леммы

`lemmas(text)`: слова и числа (`[a-zа-яё]+|\d+`) → начальная форма `pymorphy3`, ё → е. Отбрасываются предлоги,
союзы, частицы, междометия (по части речи, без ручного списка стоп-слов). Единицы измерения (`UNITS`: см, кг, шт…)
не лемматизируются — pymorphy читает «см» как «смотреть». Десятичная запятая → точка.

`lemma_key` — множество лемм по алфавиту: «разделочная доска» и «доски разделочные» дают один ключ `доска разделочный`.
Ключи пересчитываются у всех запросов при каждом пересчёте, чтобы смена правил не оставляла старые ключи.

### Частотность

`frequency` запроса = сумма по дням максимума `searched_users` по товарам за последние `frequency_days` дней данных.
Не сумма по товарам: один покупатель видит несколько товаров магазина и посчитался бы несколько раз; максимум —
оценка снизу. Для запросов без данных Ozon остаётся частотность из ручного ввода или CSV (её не затирает и наоборот:
ручной ввод не перезаписывает частотность `api`).

### Кластеры

`build_clusters`: группы с одинаковым `lemma_key`, по убыванию частотности. Группа присоединяется к кластеру,
с **главной** группой которого у неё наибольший коэффициент Жаккара ≥ `cluster_jaccard` (по умолчанию 0,75),
иначе открывает свой кластер. Сравнение только с главной группой, без цепочек:

- «доска разделочная» (2 леммы) и «доска разделочная деревянная» (3) — 2/3 < 0,75 → **разные** кластеры.
  Так и нужно: слово «деревянная» — отдельная цель для карточки.
- «доска разделочная деревянная большая» (4) к «доска разделочная деревянная» — 3/4 → тот же кластер.

id кластера стабилен между пересчётами (уникален по ключу главной группы), название — самый частый запрос главной группы.
Ручной перенос: `lock_cluster(conn, keyword_id, cluster_id)` ставит `cluster_locked`, пересчёт такой запрос не трогает.
На данных магазина (октябрь 2026): 1 815 запросов → 1 342 ключа лемм → 1 137 кластеров; одиночные кластеры —
длинный хвост, 17% частотности.

### Матрица покрытия — `coverage_matrix(conn, sku)`

Для каждого кластера запросов товара по последнему снимку карточки: есть ли **все** слова главного запроса кластера
в названии / описании / характеристиках (`in_title`, `in_description`, `in_attributes`), доля слов в каждом поле
(`shares`) и каких слов нет нигде (`missing`). Сортировка — по частотности кластера.

```bash
.venv/bin/python scripts/search_semantics.py coverage --offer 1302
```

### Приоритет — `score_pair`

```
score = частотность × (CTR(позиция 1) − CTR(текущая позиция)) × коэффициент конверсии товара
```

- CTR по позиции — кусочно-линейная кривая `ctr_curve` из настроек. Пока позиция неизвестна (без подписки — до этапа 3),
  подставляется `unknown_position` (30), и `score_details.position_known = false`. Тогда приоритет внутри товара
  по сути равен частотности.
- Коэффициент конверсии: (заказано / искавшие) товара за `frequency_days`, делённое на медиану по товарам с заказами,
  ограничено 0,5–2. Нет данных — 1.
- **Зона роста** (`score_details.growth_zone`): позиция известна и в `growth_zone` (10–50), а частотность не ниже
  медианы частотностей запросов этого товара × `growth_min_frequency_ratio`. Список: `search_semantics.py growth`.
- Ручные поля не смешиваются со score: `is_target`, `manual_priority` (в связи товар — запрос) и `keywords.priority`
  хранятся отдельно — интерфейс сортирует по ним первыми.

### Ручной ввод и CSV

```bash
.venv/bin/python scripts/search_semantics.py add "доска из кедра" "доска для хлеба" --offer 1302 --priority 1
.venv/bin/python scripts/search_semantics.py import запросы.csv
```

Добавленные вручную запросы связываются с товарами как целевые (`is_target = 1`). CSV: разделитель `;`, `,` или табуляция
(определяется сам), кодировка UTF-8 или Windows-1251, заголовки по-русски или по-английски: `запрос`/`query` (обязателен),
`артикул`/`offer_id`, `sku`, `частотность`/`frequency`, `приоритет`/`priority`. Неизвестный артикул — ошибка импорта
(весь файл не применяется).

### Подсказки поиска Ozon

Не реализованы: это сайт ozon.ru, а не Seller API, и он закрыт антибот-защитой. Каждый запрос подсказок тратит
тот же небольшой бюджет запросов, что и замер позиций (см. «Парсер выдачи»), поэтому подсказки отложены.

## Парсер выдачи

Без подписки Ozon не отдаёт позиции через API, поэтому их замеряет парсер сайта. Модули:

| Модуль | Что делает |
|---|---|
| `serp_paths.py` | **Всё знание об устройстве ozon.ru**: эндпоинт, префиксы виджетов, путь к региону, признак капчи, метки рекламы. Ozon поменял сайт — правится только он |
| `serp_parser.py` | Чистые функции без сети: проверка ответа (капча → `SerpBlocked`), разбор порции, ранжирование, строки позиций |
| `serp_browser.py` | Playwright: Chromium с профилем региона и прокси, заход на главную, запрос JSON со страницы Ozon, сохранение профиля |
| `serp_collect.py` | Прогон замеров (за флагом), план запросов, проверка региона, запись, пауза после капчи |
| `serp_profile.py` | CLI: установка Playwright, создание и список профилей регионов, сравнение cookies профилей |

Playwright — **необязательная** зависимость, её нет в `config/requirements*.txt`: ставится командой
`serp_profile.py setup` (pip + Chromium ~150 МБ) только у тех, кто включает парсер. Модули импортируют его внутри функций.

### Что известно об ozon.ru (проверено 23.10.2026)

- **Выдача — JSON:** `GET /api/entrypoint-api.bx/page/json/v2?url=/search/?text=…`. Ozon часто переадресует поиск
  в категорию (`/category/…/?text=…`) — это та же выдача. Товары — в `widgetStates["tileGridDesktop-…"]` (строка JSON,
  `items[].sku`); первая порция — 8 товаров, следующие — по ссылке `nextPage` виджета `infiniteVirtualPaginator-…`.
- **Регион — в каждом ответе:** `location.current` = `{city, uid}`, где `uid` — код ФИАС (Москва
  `0c5b2444-70a0-4932-980c-b4dc0d3f02b5`). **Отдельной cookie с регионом нет** среди видимых скрипту (`xcid`,
  `__Secure-ab-group`, `x-o3-timezone`, `ADDRESSBOOKBAR_WEB_CLARIFICATION`); без выбора адреса Ozon ставит Москву.
  Регион, судя по всему, привязан к анонимной сессии (httpOnly-cookies) — поэтому профиль = полный storage_state.
  `serp_profile.py diff msk spb` покажет, какие cookies различаются у профилей; если окажется, что одна —
  можно перейти на подстановку одной cookie.
- **Капча:** HTTP 403, `text/html`, `<title>Antibot Captcha</title>`. Появилась на **5-м запросе за минуту** из обычного
  браузера. Отсюда осторожный объём ниже.
- **Реклама:** явной метки не нашли — ни текста «Реклама», ни erid; поля `advert`/`advertLite` есть у **всех** товаров
  (это токены трекинга). Пока рекламным считается товар со строкой из `AD_LABELS`, т.е. `is_ad` = 0 почти всегда и
  `organic_position` = `position`. Сырые ответы хранятся 7 дней в `search data/serp_raw/<дата>/` — по ним правило
  уточняется, когда метка появится.

### Профили регионов

```bash
.venv/bin/python scripts/serp_profile.py setup
.venv/bin/python scripts/serp_profile.py create msk "Москва"
.venv/bin/python scripts/serp_profile.py create spb "Санкт-Петербург" --proxy-env SERP_PROXY_SPB
.venv/bin/python scripts/serp_profile.py list
```

`create` открывает окно Chromium на ozon.ru; пользователь выбирает город в шапке и нажимает Enter в терминале.
Программа одним запросом читает `location.current`, показывает город и код ФИАС (не совпал с названием — спрашивает),
сохраняет storage_state в `search data/serp_profiles/<код>.json`, снимок имён cookies с хешами значений
(`<код>.cookies.json`, сами токены туда не попадают) и строку в таблице `regions`. Список регионов — только в БД,
в коде его нет. Прокси — имя переменной `.env` (`http://логин:пароль@хост:порт`), сам адрес в базе не хранится.

### Замер — `serp_collect.py`

Включается `SERP_PARSER_ENABLED=1` в `.env`. Приложение запускает его в фоне после сбора аналитики
(`auto_collect_search`), можно и вручную; `--dry-run` показывает план без браузера.

1. Пропуск: флаг выключен; капча была меньше `cooldown_hours` назад; нет регионов с профилем; нет запросов.
2. План (`plan_queries`): до `max_queries` запросов — сначала целевые (`is_target`) по ручному приоритету, затем,
   если `fill_with_top`, остальные по `score`. Для запроса замеряются **все** связанные с ним товары — выдача одна.
3. По каждому активному региону (пауза `region_delay_seconds` между регионами): Chromium с профилем → главная Ozon
   (капча → стоп) → по каждому запросу, кроме уже замеренных сегодня (пауза `query_delay_seconds`):
   порции выдачи с паузой `page_delay_seconds`, пока не найдены все SKU запроса, не кончилась выдача или не достигнуто
   `max_pages`/`max_positions`. Повтор той же ссылки `nextPage` — стоп (защита от зацикливания).
4. **Проверка региона** — по первой порции каждого запроса: `location.current.uid` ≠ `regions.fias` → `RegionMismatch`,
   ничего по региону не пишется, в журнале — ошибка «пересоздайте профиль».
5. Запись — `positions` (upsert по `(date, sku, keyword_id, region_id, source)`, `source = 'serp'`): общая позиция,
   органическая (без рекламных выше), порция, флаг рекламы, просмотренная глубина. **Не найден — `position = NULL`,
   `found = 0`**, а не 999. Профиль сохраняется заново (Ozon обновляет cookies).
6. Есть новые позиции → `search_semantics.rebuild`: приоритеты и зона роста пересчитываются.

**Капча или блокировка** (403/429/страница Antibot) → прогон останавливается целиком, `collect_runs.status = 'blocked'`,
код выхода 3, в приложении — уведомление. Повторов нет; следующий запуск — не раньше `cooldown_hours`. Обходить капчу
программа не пытается.

Объём по умолчанию: 15 запросов × 2 региона × 1 замер в день ≈ 30 поисков, растянутых паузами на 20–30 минут.

### Позиция для приоритета

`search_semantics.serp_positions(conn, median_days)`: замеры за последние `median_days` (3) дня по всем регионам →
верхняя медиана (`median_high`), где «не найден» — хуже любой позиции. Два замера «3 и не найден» дают «не найден»:
одна удачная выдача не делает запрос «в топе». `latest_positions` берёт её, а без замеров выдачи — позицию из API
(Premium). Для приоритета «не найден» ≠ «неизвестно»: не найден — CTR 0 (максимальный прирост), неизвестно —
`unknown_position`. Сводный индекс по регионам с весом доли заказов — этап 5.

## Настройки

`search_settings.json` в корне проекта (необязателен, исключён из Git, переносится `transfer_data.py`).
Заданные в нём ключи заменяют значения по умолчанию из `search_semantics.DEFAULT_SETTINGS`; неизвестные ключи игнорируются,
повреждённый JSON — ошибка пересчёта (а не тихий откат к умолчаниям).

```json
{"cluster_jaccard": 0.75, "frequency_days": 28, "growth_zone": [10, 50], "growth_min_frequency_ratio": 1.0,
 "unknown_position": 30, "ctr_curve": {"1": 0.10, "5": 0.055, "10": 0.04, "50": 0.01, "200": 0.001},
 "serp": {"max_queries": 15, "fill_with_top": true, "max_pages": 10, "max_positions": 300,
```

## Экран «Поиск»

Раздел приложения после «Анализа». Данные — `scripts/search_view.py` (чистые функции над базой, без сети; тесты —
`tests/test_search_view.py`), отрисовка — `render_search_view` и `search_*` в `app_flet.py` по образцу «Остатков»
(`dpanel`, `dtext`, `dash_stat`, столбики как в «Анализе»). При первом входе `search_load()` читает базу в потоке
(~0,3 с); кнопка «Обновить данные» запускает `search_collect.py` задачей-процессом, после неё и после фонового сбора
данные перечитываются.

**Окна.** От последнего дня с данными запросов D: неделя `[D−6, D]`, прошлая `[D−13, D−7]`, 28 дней `[D−27, D]`.
Продажи — за те же даты, чтобы спрос и заказы сравнивались честно.

**Показатели.** Спрос магазина — сумма по запросам максимума `searched_users` по товарам за день (без двойного счёта);
спрос товара — его `searched_users`. Конверсия — заказов на 100 тыс. поисков (на 10 тыс. у товара почти всегда «0,0»).

**Тренд запроса** показывается, только если запрос был в данных не меньше 4 дней из 7 в обеих неделях
(`stable_keywords`): Ozon отдаёт по товару только 15 главных запросов в день, и редкий запрос появляется урывками —
без правила экран показывал «−100%» там, где просто был пропуск в данных.

**«Что сделать в первую очередь»** (`actions`), по весу — сколько поисков затронуто:

| Вид | Когда | Почему так |
|---|---|---|
| `conversion` | заказы −30% и больше, спрос изменился меньше чем на −15%, на прошлой неделе ≥ 10 заказов | товары находят, но не покупают — дело в карточке, цене, наличии, а не в поиске |
| `demand` | упали и спрос (≤ −15%), и заказы (≤ −30%) | товары реже показывают или сезон |
| `no_sales` | у товара ≥ 20 тыс. искавших за 28 дней и ни одного заказа | одним пунктом на все такие товары |
| `gap` | в названии нет всех слов частого кластера товара (спрос товара ≥ 100 за 28 дней) | один пункт на кластер со списком артикулов |
| `drop` | спрос товара −30% и больше при ≥ 500 искавших на прошлой неделе | один пункт на все такие товары |
| `rising` | запрос +50% за неделю, ≥ 200 поисков, устойчивый, и хотя бы половина его слов есть в названиях магазина | «стол» у разделочных досок не сигнал |

Пробел (`gaps`) учитывается, только если хотя бы половина слов кластера уже есть в **названии** товара — иначе это,
скорее всего, чужой запрос. Если слов нет нигде в карточке («пластиковый» у деревянной доски), нужно больше половины
и вес такого пункта втрое ниже: это может быть другой материал или назначение, и текст подсказки предупреждает об этом.

**Вкладки.** «Запросы» — кластеры по спросу за 28 дней (поиск по названию, «Только целевые», по 40 строк),
раскрытие кластера — формулировки со звёздочкой «целевой» (`search_view.toggle_target` → для всех связанных товаров
и пересчёт приоритетов). «Товары» — таблица и экран товара (`load_product`). «Позиции» — состояние парсера и таблица
«запрос × регион» с изменением к замеру неделю назад и подсветкой расхождения регионов на 20+ мест.
