# 04. Месячный отчёт и бизнес-сводка

Код: `scripts/Monthly_sales_report.py`. Результат: `reports/Ozon/<Год>/<Месяц> <Год>.xlsx`
(например, `reports/Ozon/2026/Сентябрь 2026.xlsx`; пути — `scripts/report_paths.py`). Этот файл — источник для бизнес-сводки и графиков
в приложении, ABC/XYZ-анализа, расчёта рекомендованных цен (ставки комиссии и логистики
берутся из отчёта за прошлый месяц) и AI-ассистента.

## Кто запускает

| Откуда | Как |
|---|---|
| «Бизнес-сводка» → обновить | `job("Обновление бизнес-сводки", [... "Monthly_sales_report.py", "--month", M, "--year", Y], prompt_for_costs=True)` |
| График / ABC/XYZ, если не хватает месяцев | `build_missing_chart_reports` — по очереди для каждого недостающего месяца, останавливается на первой ошибке |
| Рекомендованные цены, если нет отчёта за прошлый месяц | `recommended_prices.generate_monthly_report` через `subprocess.run` |
| Консоль | `python scripts/Monthly_sales_report.py [--month M --year Y] [--ozon-promotion-cost X] [--external-marketing-cost Y]` |

Без `--month/--year` скрипт спрашивает месяц и год в терминале.

## Последовательность

```
main()
 ├─ date_range_for_month(M, Y) → "YYYY-MM-01T00:00:00Z" … "YYYY-MM-<последний>T23:59:59Z"   (UTC!)
 └─ with create_session() as session:                      # ReportSession, см. 03
      ├─ get_orders()        — FBS, v4/posting/fbs/list
      ├─ get_fbo_orders()    — FBO, v3/posting/fbo/list
      └─ with atomic_output_path(reports/Ozon/<Год>/<Месяц> <Год>.xlsx) as temporary:
           ├─ to_excel(...)                 → лист «Заказы», лист «Расходы вне заказов»
           └─ calc_business_indicators(...) → блок показателей P/Q, лист «Кампании»
```

Файл отчёта публикуется **только целиком**: всё пишется во временный `~tmp_*.xlsx`, и лишь
после успешного расчёта показателей он заменяет старый отчёт. Любая ошибка (сбой страницы,
постоянный 429, ошибка баланса) — код выхода 1 и сообщение `❌ …`; прежний отчёт остаётся.

### 1. Заказы

`_get_postings` обходит страницы по курсору; повтор курсора или `has_next=true` без нового
курсора — ошибка. Для FBS и FBO запрашиваются статусы
`awaiting_packaging, awaiting_deliver, delivering, delivered, cancelled` и блоки
`analytics_data`, `financial_data`. `_fetch_posting_page` приводит ответ к единому виду:
- `p["__schema"] = "FBS" | "FBO"`;
- `products[].price` из `{amount, currency}` → строка-число, валюта → `currency_code`;
- `financial_data.products[].commission` → `commission_amount`, `commission_percent`, `currency_code`.

Из заказа отчёт берёт только `posting_number`, `status`, дату, `products` (название, артикул,
количество, цена, `is_marketplace_buyout`) — **комиссию и выплату берёт из начислений, а не из заказа.**

### 2. Начисления

`get_transactions_by_posting` (`Monthly_sales_report.py:308`) идёт по **каждому дню** периода и
загружает `/v1/finance/accrual/by-day` с пагинацией `last_id`. Конец периода обрезается до сегодняшней
даты (UTC).

Период начислений = месяц **плюс 21 день** (`ACCRUAL_LOOKAHEAD_DAYS`, `to_excel`). Причина: Ozon
проводит начисление «продажа с комиссией» через 2–19 дней после отгрузки (медиана ~6 дней, проверено
на реальных данных за август). Без запаса заказы конца месяца выглядели бы «ожидающими расчёта».
Запас ничего не задваивает: начисления привязываются к номеру отправления, а в отчёт попадают только
отправления этого месяца.

Для каждого начисления с номером отправления сохраняется запись:

| Поле | Откуда | Смысл |
|---|---|---|
| `amount` | `total_amount` | Итог начисления со знаком (что Ozon заплатит или спишет) |
| `sale_commission` | сумма `posting.products[].commission.sale_commission` | Комиссия за продажу (обычно отрицательная) |
| `accruals_for_sale` | сумма `commission.seller_price` | Цена продажи по начислению |
| `is_return` | `seller_price < 0` | Возврат: Ozon оформляет его отдельным начислением с отрицательной ценой |
| `has_commission_data` | есть ли у начисления блок `commission` | Отличает «продажа обнулена возвратом» от «начисление продажи ещё не пришло» |

**Расходы вне заказов.** Начисления категории `NON_ITEM` без номера отправления (или с номером без
дефиса — номер поставки или кампании) собираются отдельно (`_is_account_charge`): кросс-докинг,
обработка поставки, ранний вывод средств и т. п. В лист «Расходы вне заказов» попадают только
**дни самого месяца** (запас в 21 день сюда не входит). Коды, которые уже посчитаны другими строками
и в прибыль повторно не идут (`ACCOUNT_CHARGES_COUNTED_ELSEWHERE`): 41 и 75 — реклама,
46 — хранение FBO. Названия кодов — `ACCOUNT_CHARGE_NAMES`.

### 3. Лист «Заказы»

`to_excel` (`Monthly_sales_report.py:440`): одна строка на отправление.

| Колонка | Значение |
|---|---|
| A «Статус» | Статус Ozon, но пересчитанный (см. таблицу ниже) |
| B «Номер заказа» | `posting_number` |
| C «Название товара» | название первой позиции |
| D «Артикул» | все `offer_id` через запятую; если один — числом (`_artikul_to_number`) |
| E «Количество шт.» | сумма `quantity` |
| F «Цена продажи» | сумма `accruals_for_sale` по начислениям; если 0 и у начислений нет данных о комиссии — цена из заказа × количество |
| G «Комиссия за продажу Ozon» | сумма `sale_commission` |
| H «Логистика (Включает операционные ошибки продавца)» | `amount − price − sale_commission` — всё, что не цена и не комиссия |
| I «Сумма начисления» | сумма `amount` |
| J «Себестоимость» | −(себестоимость × количество), только для проданного |
| K «Прибыль» | см. ниже |
| L «Дата отгрузки» | FBS — `shipment_date`; FBO — первое из `in_process_at`, `shipment_date`, `created_at`, … |
| M «Схема» | FBS / FBO |

Знаки: комиссия и логистика — расходы со знаком минус, поэтому **цена + комиссия + логистика = начисление**.

Себестоимость берётся из `costs.xlsx` (`load_cost_map`): колонка ключа — первая из
`prefix, префикс, код, артикул, offer_id`, колонка цены — первая из `cost, себестоимость, цена, стоимость`.
Ключ нормализуется (`12345.0` из Excel → `12345`). Сопоставление — **точное по артикулу**
(комментарий про префиксы устарел). Нет артикула в справочнике — себестоимость 0.

Пересчёт статуса и значений (`to_excel`, строки ~565–646):

| Статус Ozon | Условие | Статус в отчёте | Начисление | Комиссия / логистика | Себестоимость | Прибыль |
|---|---|---|---|---|---|---|
| `delivering` | — | `delivering` | сумма | «-» | 0 | «-» |
| `awaiting_packaging` | — | `awaiting_packaging` | «-» | «-» | 0 | «-» |
| `cancelled` | — | `cancelled` | сумма | «-» | 0 | = начисление (штрафы, логистика отмены) |
| `delivered` | есть начисление-возврат | **`returned`** | сумма | считаются | 0 | = начисление |
| `delivered` | нет данных о комиссии ни в одном начислении | **`ожидает расчёта`** | сумма | текст «Ожидает расчёта Ozon (…)» | 0 | тот же текст |
| `delivered` | обычный случай | `delivered` | сумма | считаются | −себестоимость | начисление + себестоимость |
| прочие (`awaiting_deliver` и др.) | — | без изменений | «-» | «-» | 0 | «-» |

Почему так:
- **Возврат после доставки Ozon в статусе не показывает** — отправление навсегда остаётся `delivered`.
  Единственный надёжный признак — начисление с отрицательной `seller_price`. Статус `returned` нужен,
  чтобы не списать себестоимость товара, который вернулся. Отрицательная прибыль сама по себе статус
  не меняет.
- **«Ожидает расчёта»** — продажа доставлена, но начисление с комиссией ещё не пришло (попало в
  следующий месяц дальше запаса в 21 день) или это трансграничный заказ (`is_marketplace_buyout`),
  который Ozon рассчитывает по своему графику. Выручку мы ещё не знаем, поэтому себестоимость
  не списываем (принцип соответствия), а строку выделяем, чтобы её было легко найти и перепроверить.
  Подпись различает два случая: «трансграничный заказ» и «начисление ещё не пришло».

### 4. Блок показателей (колонки P/Q)

`calc_business_indicators` (`Monthly_sales_report.py:787`) пишет в лист «Заказы» пары «название — значение»
в колонки P и Q. **Названия — это контракт с приложением**: `read_business_metrics` (`app_flet.py:661`)
читает строки 1–70 колонок P–Q и ищет показатели по тексту. Переименование строки ломает сводку.

| Ячейка | Показатель | Формула |
|---|---|---|
| Q1 | Общая выручка | сумма F по строкам `delivered` и `returned` |
| Q2 | Чистая прибыль | сумма K − продвижение Ozon − внешний маркетинг − хранение FBO + расходы вне заказов (они отрицательные) |
| Q3 | Итоговая себестоимость | сумма J (отрицательная) |
| Q4 | Рентабельность по чистой прибыли % | Q2 / Q1 × 100 |
| Q5 | Валовая прибыль | Q1 + Q3 |
| Q6 | Рентабельность по валовой прибыли % | Q5 / Q1 × 100 |
| Q7 | Операционные расходы | Q5 − Q2 |
| Q8 | Продвижение Ozon | реклама (Performance API или ручной ввод) **+ звёздные товары** |
| Q9 | Звёздные товары | из баланса (входит в Q8, показан отдельно) |
| Q10 | Внешний маркетинг | ручной ввод |
| Q11 | Средний чек | средняя F по `delivered` с ненулевой ценой |
| Q12–Q14 | Всего заказов / отменённых / доставленных | по статусам |
| Q15, Q16 | Комиссии %, Логистика % | среднее по строкам |G|/F и |H|/F |
| Q17 | Расход хранения FBO | из баланса |
| Q18, Q19 | Возвращённых / в доставке | по статусам |
| Q20, Q21 | Комиссии сумма, Логистика сумма | сумма |G| и |H| |
| Q22 | Заказы, ожидающие расчёта Ozon | число строк «ожидает расчёта» |
| Q23 | Расходы Ozon вне заказов | модуль суммы листа «Расходы вне заказов» без кодов 41/46/75 |
| Q24… | «Вне заказов — <вид>» | разбивка по видам |
| далее | Сверка с балансом | выплачено Ozon, входящий/исходящий баланс, начислено по балансу, наш расчёт (сумма I), расхождение, комиссия за ранний вывод, справка о методике |
| далее | Прочие комиссии и услуги Ozon | до 12 крупнейших услуг из баланса |

**Сверка с балансом — не ошибка, а разные методики.** Баланс Ozon группирует по календарным дням
проводок, наш отчёт — по отправлениям месяца (с доборкой начислений задним числом). Небольшое
расхождение нормально; большое стоит проверить через Q22.

### 5. Баланс: звёздные товары, хранение, выплаты

`balance_report.get_monthly_balance_reports` делит месяц на отрезки по ограничению Ozon в 30 дней:
1–30 число и, если в месяце 31 день, отдельно 31-е. Ошибка любого отрезка — `RuntimeError`, отчёт
не создаётся (пропавший отрезок выглядел бы как нулевые расходы).

- Звёздные товары: `cashflows.star_products.amount.value`, иначе сумма услуг, в названии которых есть
  `star`/`звезд`.
- Хранение FBO: `cashflows.product_placement_in_ozon_warehouses.amount.value`, иначе сумма услуг
  с `placement`/`warehouse`/`хранен`/`размещ` в названии.
- `summarize_month` — официальные цифры Ozon для сверки (Q24 и далее).

В отчёте все три показателя берутся по модулю.

### 6. Реклама

- Расход на продвижение: `performance_api.get_cpc_campaigns_for_month` — все кампании периода
  (любой тип оплаты), статистика за месяц. Если ключи Performance API не заданы, токен не получен
  или кампаний нет — 0, без ошибки.
- Лист «Кампании»: `create_campaigns_sheet` → `get_campaigns_data_for_excel` (ID, название, состояние,
  бюджеты, расход, показы, клики, CTR, цена клика, заказы, ДРР). Ошибка листа печатается как
  предупреждение и **не роняет** отчёт.

### Ручной ввод маркетинга

Если `--ozon-promotion-cost` не передан и из API пришёл 0, скрипт печатает
«Введите сумму затрат на продвижение Ozon за месяц (или Enter для 0):» и читает `input()`.
Внешний маркетинг спрашивается всегда, если не передан `--external-marketing-cost`.

Вопрос задаётся, только если stdin — терминал **или** задано `OZONREPORTX_UI_PROMPTS=1`.
Иначе подставляется 0 с сообщением в логе. Приложение ставит эту переменную для «Обновления бизнес-сводки»
и подготовки отчётов для графика и отвечает через диалог (протокол вопросов — в [02](02-app-architecture.md#вопрос-пользователю-из-дочернего-процесса)).
`recommended_prices.generate_monthly_report` переменную не ставит: там маркетинг всегда 0 —
для ставок комиссии и логистики он не нужен.

### 7. Оформление: отчёт нового вида (`report_design.py`, `report_book.py`)

Последний шаг перед публикацией файла — `apply_design_file`: листы с данными переименовываются и прячутся,
поверх строятся листы для человека.

| Видимый лист | Что на нём | Скрытый лист с данными | Прежнее имя |
|---|---|---|---|
| «Сводка» | крупные цифры, «из чего сложилась прибыль», заказы по статусам, расчёты с Ozon, топ-10 товаров | «Данные» | «Заказы» |
| «Заказы» | таблица с фильтром, статусы по-русски, итог по видимым строкам | «Данные кампаний» | «Кампании» |
| «Реклама» | кампании с расходом сверху, без расхода — свёрнуты | «Данные расходов» | «Расходы вне заказов» |
| «Расходы вне заказов» | итог по видам и все операции | | |

- **Раскладка скрытых листов не меняется** (A–M, P:Q, `Q15`, S:Y) — это по-прежнему контракт со всеми, кто
  читает отчёт. Видимые листы программа не читает; они строятся из скрытых заново (`render`) — и при формировании,
  и при каждой сверке выплат, поэтому ничего своего не хранят.
- **Читать отчёт — только через `report_book.data_sheet` / `data_sheet_name`:** есть «Данные…» — берётся он,
  иначе прежний лист. Так приложение, расчёт цен, ABC/XYZ, AI-ассистент, органика и сверка читают и отчёты
  старого вида (до 3.5.0), и нового. Отчёты WB не меняются: листов «Данные…» в них нет.
- «Из чего сложилась прибыль» сходится с Q2 до копейки: «Отмены, возвраты и прочее» — остаток начислений по заказам
  после выручки, комиссии и логистики; заказы «ожидает расчёта» не входят, как и в Q2.
- Перевести старые отчёты в новый вид без запросов к Ozon: `.venv/bin/python scripts/report_design.py`
  (отчёты нового вида пропускаются).

### 8. Сверка выплат (колонки S:U и W:Y)

После публикации отчёта `main()` вызывает `payout_settlement.update_reports` — пересчёт идёт **по всем**
месячным отчётам Ozon в `reports/Ozon/` сразу. Сбой сверки печатается как
предупреждение и не отменяет сохранённый отчёт. Отдельно без пересборки отчётов:
`.venv/bin/python scripts/payout_settlement.py`.

- **Долг Ozon** по месяцу — «Итоговая себестоимость» (по модулю) и «Чистая прибыль» из блока P/Q.
  Убыточный месяц долга по прибыли не создаёт.
- **Выплаты** — `total.payments` из `v1/finance/balance`. API отдаёт их суммой за период без даты, поэтому
  дата находится делением периода пополам до одного дня. Выплаты закрытых месяцев кэшируются
  в `balance reports/payouts.json`; API опрашивается заново только за текущий месяц. Чтобы перечитать
  всё, удалите этот файл.
- **Распределение — FIFO:** выплаты по дате гасят месяцы от старого к новому, внутри месяца сначала
  себестоимость, потом прибыль. Одна выплата может закрывать несколько месяцев — тогда в U пишется
  «(часть выплаты N ₽)».
- **S:U** — дата выплаты, сумма из неё, на что ушла. **W:Y** — себестоимость (строки 1–2) и прибыль (4–5):
  начислено, закрыто выплатами, осталось закрыть. `X7` — «Да», когда обе дельты нулевые: Ozon рассчитался за месяц.
  `X9` — всего выплачено с начала магазина; `X10` — выплачено сверх начислений по отчётам, если есть.
- Месяц без файла отчёта в распределении не участвует: его выплаты уйдут на следующий месяц.
  Поэтому отчёты нужны за все месяцы с начала магазина.

## Нюансы и подводные камни

- **Границы месяца — в UTC.** И заказы (`since/to`), и начисления по дням считаются в UTC.
  Заказ, принятый 1-го числа в 01:00 по Москве, попадёт в предыдущий месяц.
- **Фильтр заказов и колонка даты — разные даты.** Документация не уточняет, по какой дате работает
  `since/to`; курсор v4 сортирует по `in_process_at`, так что, по всей видимости, отбор идёт по дате
  принятия в обработку. В колонку L для FBS пишется `shipment_date` — она может выходить за пределы месяца.
- **Поздние возвраты теряются.** Начисление, пришедшее позже 21 дня после конца месяца, не попадёт
  ни в этот отчёт (вне окна), ни в следующий (отправление не из того месяца). Чтобы учесть позднее
  начисление, отчёт за старый месяц надо сформировать заново.
- **Старые отчёты не пересчитываются сами.** Сводка читает сохранённые числа; после изменения правил
  расчёта старые месяцы нужно сформировать повторно.
- **Тяжёлая загрузка.** Начисления — минимум один запрос на каждый из ~52 дней. С паузой 0,5 с и
  несколькими страницами в день отчёт за месяц занимает минуты; при 429 сессия замедляется до 5 с между запросами.
- **Себестоимость на дату формирования.** Берётся текущий `costs.xlsx`, а не тот, что был в том месяце.
